- LLM 裁判：用户指定 `https://api.codexzh.com/v1` 的 GPT 5.6 SOL。该服务的直接模型 ID `gpt-5.6-sol` 明确拒绝当前仓库使用的 Chat Completions 协议；兼容别名 `cc-gpt-5.6-sol` 已通过同一协议的 JSON 冒烟请求（HTTP 200）并返回 `model=gpt-5.6-sol`。正式配置暂用 `cc-gpt-5.6-sol` 作为请求 ID，同时记录返回身份 `gpt-5.6-sol`；评分生成、长输入和批量 rubric 兼容性仍须非实验题预检。裁判身份作为本版新配置冻结，不沿用原 Claude 评分配置，也不将代理模型名当成官方身份认证。
- IFEval/IFBench 使用固定版本的作者程序化 checker，GPT 裁判不替代这些原生指标。
- 密钥仅通过运行时凭据注入，不进入协议、代码、论文或日志。
- 六份原始数据均已存在，SHA256 与原 v5 清单一致：RR 为 `outputs/researchrubrics_live_20260930/processed_data.jsonl`；DSQA 为 `dataset/deepsearchqa/DSQA-pinned-v3.csv`；DRBII、WritingBench、IFEval、IFBench 分别位于对应 `dataset` 子目录。保留 60 EVO、30 VAL、273 TEST 的全部成员，共 363 道不同题目。
- 当前未找到已验证覆盖正式题目的冻结证据包。研究类任务须先准备各方法共享的公开证据，记录来源、检索配置和哈希；公开任务投影及历史答案不能代替证据包。用户已选择使用可用的公开检索/抓取替代服务：先在非实验任务上验证可用性，再固定具体检索服务、HTTP 页面提取器、查询/抓取参数和依赖版本。现有 Serper/Jina 凭据未配置，不作为本轮启动前提；正式准备与运行期间不根据答案质量临时切换来源。

## 参数基线（预检通过后冻结）

下面是正式首批拟采用的参数；它们是可审计的资源与请求边界，不是用来人为限制单个角色调用次数的规则。长上下文和裁判 JSON 兼容性通过合成任务预检后才写入正式身份。

| 参数 | 生成/规划/执行 | 裁判 | 说明 |
|---|---:|---:|---|
| 模型 | `deepseek-v4-flash-vision` | `gpt-5.6-sol` | 记录请求 ID、返回模型字段和服务端指纹 |
| 温度 | `0` | `0` | 不主动设置 `top_p`、`seed`、frequency/presence penalty；保留服务端默认值并记录 |
| 单次输出上限 | meta/global/local `16,000`；exec `8,192` | `16,000` | `max_tokens` 是输出上限，不是上下文窗口 |
| 目标总上下文 | `131,072` tokens | `131,072` tokens | 服务端模型列表未声明窗口；预检失败则降到服务端实测可接受值并重新冻结 |
| 输入预算 | 目标窗口减去该次输出上限及安全余量 | 同左 | 超长账本按固定、与结果无关的摘要规则处理；不能按质量挑选保留内容 |
| 单请求超时 | `180 s` | `180 s` | 超时记录失败；恢复同一槽位，不按质量重生 |
| 单任务 wall-clock | `900 s` | 由任务槽位统一计时 | 包含多轮角色调用、工具与 Writer 修订；排队时间另记 |
| 单任务 token 上限 | `2,000,000` | 计入同一任务账本 | 保留硬 token/时间/成本停止条件；模型调用数、工具数、协作轮数不设固定硬上限 |
| 请求并发 | 预检从 `2` 个在途请求开始 | 同左 | 只控制吞吐和限流，不改变轨迹顺序或样本数 |
| SDK 重试 | `max_attempts=1`，SDK `max_retries=0` | 同左 | 网络恢复使用幂等槽位重启；不静默产生第二份答案 |
| 角色/工具 | 最多 3 个角色、角色并发 `2`；工具按冻结清单 | 只读私有评测记录 | 正式任务使用冻结公开证据；证据准备的公开检索/抓取是单独阶段 |
| 预执行/归因 | `local_rounds=1` 作为阶段入口 | 不参与答案生成 | 阶段内部调用由 token、时间和成本预算停止，实际次数完整计量 |
| 候选/修复 | `candidates=1`；执行开始前最多 2 次接口修复 | 不替换已提交产物 | 执行角色开始后失败不整队重放 |

上下文长度需要特别区分三件事：服务端可接受的最大窗口、一次请求的输入 token 数、以及 `max_tokens` 输出上限。当前 `OpenAIServerModel` 会把完整消息发送给服务端，旧配置没有显式输入窗口或截断策略；因此在新增上下文计量和固定摘要规则前，不启动正式题。DeepSeek 的实测 planning 需要 `16,000` 输出预算；`4,096` 会因 JSON 被截断，不能作为正式 planning 上限。模型返回的 reasoning 字段不主动拼入下游账本，除非协议明确记录；是否启用 provider-specific thinking/reasoning 参数，等两个端点的合成预检通过后固定。

Meta-Agent 的 budget-aware 设计也须通过合成预检：全局分析和协调应读取实时 token 账本（已用、在途预留、剩余）及单次输出上限，输出包含预计输入/输出 token、调用/工具数、通信量、后续阶段预留和权衡理由的 `budget_plan`；计划与预留不能超过实时余量。预计调用数仅作估计，仍不限制固定协作轮数。确认 Agent 反思能读取自身实际成本，预估与实测分开保存，未知价格为 null，再冻结对应代码、prompt 与配置。预算策略不改变既定 VAL 质量选版规则或正式槽位数。

## 按顺序准备

1. **先补齐新版执行工程。** 取消角色、团队、任务模型调用次数硬上限及旧 single-pass 限制；支持工具结果回送、角色再次调用、Writer 工具及多轮修订、账本协作；保留统一 token/超时预算、公开输入边界与实际调用计量。Initial、Selected、固定 rubric-MAS 使用匹配的多次调用执行契约，Direct/原生 JIT 保留各自执行组织。
2. **补齐评分和注册。** 在正式入口接入 WritingBench、IFEval、IFBench，固定评分代码及依赖；保留 RR 有符号权重、DSQA F1、WritingBench 原生量表、DRBII 满足率与 blocked rate、IFEval strict 和 IFBench loose 主指标。新增独立版机器协议，沿用原成员及源内题序，注册九条轨迹、单产物 VAL/TEST、按理论范围规范化的本源选版，以及完整三来源迁移矩阵。
3. **实现并发与恢复。** 同一 EVO 轨迹依序写库，九条轨迹可并行；checkpoint 冻结后异步评 VAL，worker 各自读取不可变快照；按轨迹完成全部候选后选版。静态 TEST 与 EVO/VAL 可重叠，已确定 Selected 的 TEST 与其他轨迹 VAL 可重叠。全部 TEST 槽位登记成功或失败终态并封存后才评分。增加原子任务领取、幂等产物提交、缓存身份检查和中断恢复。
4. **使用非实验题验证。** 用合成任务验证多次调用、工具与 Writer 修订、经验更新/检索、三个新增 scorer、异步隔离、选版屏障、封存屏障和恢复。两个 API 分别测试 JSON、长输入与小规模并发；检索准备也使用合成公开任务预检。EVO/VAL/TEST 与 reserve 均不用于修代码或挑配置。请求并发先从 2 开始验证，再按稳定性冻结正式在途请求上限；这属于吞吐设置，不是单任务调用次数限制。
5. **通过预检后冻结正式身份。** 冻结代码、prompt、配置、模型/裁判身份、数据/证据/协议哈希、预算、限流、工程重试与完整库存。同步论文正文、实验协议、附录和结果模板中的独立进化、多次调用、分源迁移及统计口径。正式实验开始后不依据 VAL/TEST 调代码或资源；需要改动时登记新版本并保留旧记录。

## 首批怎么跑

正式首批先启动 **run 0 的 RR、DSQA、WritingBench 三条轨迹**，各从空经验库出发：

| 首轮 EVO/VAL 工作 | 槽位数 |
|---|---:|
| 三个来源的 C0，分别评价本源全部 10 道 VAL | 30 |
| 每个来源按冻结题序执行前 5 道 EVO | 15 |
| 三个来源的 C5，分别评价本源全部 10 道 VAL | 30 |
| **首轮 EVO/VAL 合计** | **75** |

三条 EVO 链可并行；每条链内部按题序执行，C0/C5 的 VAL 读取冻结快照异步进行。上述 75 个槽位是原正式库存的一部分，不是额外 pilot；不因分数高低换题、加 run 或调整方法。

身份冻结后，四种静态方法的 TEST 生成也可进入并行队列，其工作量另计入原 TEST 库存。run 0 首轮结束后继续 C10/C15/C20；本轨迹全部 VAL 结算后选出完整状态，再启动该状态的本源 TEST 与三个外部目标的迁移 TEST。按固定资源调度继续 run 1/2，保持全部三次运行，无须等所有来源选版后才生成 TEST。

第一阶段可报告工程状态、真实调用/token、EVO 更新记录与 VAL 记录；正式 TEST 分数仍须等待全库存统一封存，不提前查看部分 TEST 分数指导后续工作。
