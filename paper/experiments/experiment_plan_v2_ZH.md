# JIT Compose 论文实验计划与协议

本协议将“逐题直接更新经验”和“定期选择部署 checkpoint”分开。前者属于方法的进化过程，后者属于实验中的模型选择过程；不恢复单条经验的 accept / hold / reject。下述数量和规则作为 v2 的确定设计，尚未执行，不代表已有性能结果。

机器可读协议见 `protocol_v2.json`，完整题目 ID、进化顺序和分批清单见 `splits_v2.json`。旧 v1 不覆盖。新协议保持 `launch_allowed=false`，直到文末实现与隔离检查通过，并收到正式启动要求。

## 核心决定

| 项目 | 固定设置 |
|---|---|
| 数据 | ResearchRubrics 的已固定 101 题版本；自定义任务级划分 |
| Development | 18 题，保留既有暴露与 pilot 隔离记录 |
| Evolution | 30 题，每次独立进化只过一遍，不重复刷同一道源题 |
| Validation | 固定 20 题，每次都评完整集合，不滚动、不按得分换题 |
| Test | 固定 33 题，仅用于最终冻结评价 |
| 独立进化次数 | 3 次，从空经验库出发；顺序种子为 20261001、20261002、20261003 |
| 每次进化长度 | 30 个源任务位置，共 6 批，每批 5 题 |
| Checkpoint | C0、C5、C10、C15、C20、C25、C30，共 7 个 |
| 每个 checkpoint 的 val | 20 题 × 2 次独立完整答案生成，共 40 个任务执行单元 |
| 筛选候选范围 | 本次进化的全部 7 个完整经验库 checkpoint，包含 C0 |
| 后续进化起点 | 最新进化状态，不回退到当前 val 最优状态 |
| 最终选择 | 每次进化各选一个状态，3 次运行全部报告，不挑最好的一次 |
| Test 重复数 | 每个进化状态每题 3 次；静态 baseline 每题共 3 次，跨进化运行共享 |

30/20/33 沿用此前未执行草案的题目成员，目的是避免方法调整后重新挑题；此处重新采用的是任务分配，不是旧的逐条验证规则。它不是 JIT 或 ResearchRubrics 的官方 train/val/test split。全部 ID、来源哈希与 3 份具体题序已经落盘，不依赖运行时随机抽样。

本实验不训练模型参数。“进化 30 次”准确含义是处理 30 个预注册源任务，最多直接写入 30 次经验。没有提案、执行失败、评价不完整或结构检查失败都消耗对应位置，不补抽到“成功更新满 30 次”。数据库 version 因此不一定等于 C 的下标。

## 为什么采用完整固定的 val

每 5 题形成一个**累积状态**，例如 C10 包含前 10 题产生的全部有效直接写入，而不是单独的第二批经验。验证的单位是完整的 rubric、organization、execution 三个经验库及其固定依赖版本。

每个新 checkpoint 都用同一组完整的 20 道 val 题。不能只测最新 5 道进化题，也不能只测“最近筛出的验证批次”。否则不同 checkpoint 的分数对应不同题目，难以判断变化来自经验还是难度；在源题上验证还会混入记忆效应。

历史 checkpoint 的评分缓存并保留，不需要每轮把旧状态全部重新运行。比如 C15 出现时，只新增 C15 的 40 个执行单元，再与 C0、C5、C10 的固定结果比较。若 C10 与 C5 的完整状态及运行配置哈希完全相同，复用原结果并记录 `reused_from`，不能重复抽样制造更多挑选机会。

## 每次独立进化的执行顺序

1. 冻结代码、prompt、模型与工具配置、公共参考 harness 库、证据包、划分与 selector。创建独立空经验库，保存并验证 C0。
2. 严格按该运行的预登记题序，串行处理 5 个源任务。每题提交答案后评价和归因，首条符合结构与证据约束的提案直接写入。
3. 保存当前完整状态为下一个 checkpoint。用独立只读连接运行完整 val，不生成归因或提案，不修改经验库。
4. selector 保存数值结果及当前最优 checkpoint 的索引。val 答案、rubrics、轨迹和分数不能提供给进化 agent，也不能供人工中途修改实现。
5. 从最新进化状态继续处理下一批，而不是从 val 最优状态继续。重复至 C30，不按分数早停、不追加题目、不追加 checkpoint。
6. 完成固定 30 个位置后，封存该次运行的最终选中状态和 C30。所有方法与运行的选择锁定后才进入 test。

这是单条进化轨迹上的 checkpoint selection，不是 beam search，不是“从最近选中的几个状态继续繁殖”，也不是另一种单条经验接纳机制。已有回滚 API 不用于本实验的进化调度。

## Val 的排名与失败规则

正常情况下，checkpoint 的验证分数是 20 道题的官方任务分数均值，每题先平均 2 份独立答案的分数。不是同一份答案让 judge 打分两次，也不是对 40 份答案取最高分。

固定 40 个 task-repeat 单元中，至少 36 个必须取得完整官方评价，该 checkpoint 才可参与最终选择。少于 36 个只表示其验证完成度不足；仍然保留原状态和全部失败记录，不改变进化轨迹。没有任何 checkpoint 满足条件时，该运行标为 inconclusive，不能用 test 补选或只报告另外两次运行。

对于满足完成度条件但仍有缺失的 checkpoint，采用保守筛选指标：完整单元使用真实官方分数，缺失单元使用该题可行下界

`L(task) = sum(negative criterion weights) / sum(positive criterion weights)`。

40 个单元均保留在分母中。下界只写入 `selection_utility`，附缺失标记；`official_score` 仍为 null，不能伪造为观测分数。正权重分母为零时保留固定官方评价器的零分与标志，区间为 `[0,0]`。完整时该筛选指标就是官方均分；不完整时必须称为“保守 checkpoint 筛选分数”，并同时报告真实评价完成数与全量均分上下界。

排序固定为：先求所有可选状态的最高筛选分数 `U_max`，将分数不低于 `U_max - 1e-12` 的状态列入同分集合；再按完整评价数更多 → 较早的 checkpoint → 状态哈希排序。不能用不具传递性的逐对容差比较。C0 可以获选；若它获选，必须如实报告没有选出优于初始状态的经验库。

不重跑低分答案，不因格式或代码错误重采样。judge 对冻结答案的某一条 criterion 遇到连接失败、超时或 HTTP 408/429/5xx 时，允许等待 30 秒后重试完全相同的请求一次；已返回有效判分的条目不重判。两次尝试全部计费。其他 construction/execution 模型请求没有自动重试，已有结构响应纠正及最多两次角色调用前的 harness 接口修复单独记录，不属于改善低分。

## 最终测试与统计

主比较是本方法的 val 选中状态相对初始空经验状态的质量变化。3 个独立进化状态各测全部 33 道 test，每题独立生成 3 份答案，共 297 个注册执行单元；不能只挑表现最好的进化运行或答案。

初始状态与各静态 baseline 每题只生成 3 份答案，共 99 个执行单元，其结果在 3 次进化运行的比较中共享。不能把同一份静态答案复制成 9 个独立样本。额外预注册测试每次运行的 C30，共 297 个单元，用于区分“直接累积经验的效果”和“checkpoint 选择的效果”。若选中状态恰为 C0 或 C30，则按预定的完全一致状态规则复用答案，记录实际节省，不重复抽样。

全部必做方法、消融和 G/GO 的代码与条件必须在首次 test 提交前冻结。允许按模块分批计算，但只有所有预登记 test 答案都提交并封存后才释放评分；不能先看主表再实现或调消融。test 过程只读，无归因、无经验更新，后续 test 题不能读取前面题的评分。

每道题的主差值为：`mean(3 个进化状态 × 3 次答案的分数) - mean(初始状态 3 次答案的分数)`。以 33 道完整题目为抽样单位，配对 bootstrap 10,000 次，种子 20261001，报告 95% 区间；保留方法配对及重复结构，不把 rubric 条目或调用数当样本数。另外逐一报告 3 条进化轨迹的 checkpoint、测试效果及运行间离散程度。

主检验为 selected 对 C0 的双侧配对任务 sign-flip 检验，100,000 次，种子 20261001。selected 对 JIT-matched 和 rubric-fixed 的两个次级检验做 Holm 校正。三项进化消融与 G/GO 的四个机制检验另成一组做 Holm 校正，全部报告。

若 test 仍有不完整评价，保留所有题目与空值，报告完成率、故障类别、总体分数上下界及配对差值界限，不用只含成功题的均分宣称方法更好。33 题仍是有限规模的自定义子集，增加重复调用并不增加独立题目数，不据此宣称全面 SOTA。

## 论文实验矩阵

| 模块 | 条件 | 要回答的问题 |
|---|---|---|
| 主表 | ours C0、ours selected、ours C30 | 是否能积累有效经验，选择是否优于直接用终态 |
| 主表 | Direct、JIT-matched、rubric-guided fixed | 相对单调用、原生 JIT 路径与固定组织的增益及成本 |
| 消融 | 无显式 rubrics | 显式质量要求是否有用，而非仅一般任务理解 |
| 消融 | global-only planning | 局部参与组队是否有用 |
| 消融 | global-only attribution | 局部归因是否带来可复用经验 |
| 机制 | G 对 GO | 同样 rubrics，组织生成阶段可见它们是否带来额外收益 |
| 稳定性 | 7 个 checkpoint 的完整 val 曲线与 3 条进化轨迹 | 是否退化、依赖题序、选中了哪个阶段 |
| 人工审计 | 固定 10 道 test 的匿名答案对照 | judge 结论和证据质量是否可信 |

三项进化消融均从独立空经验库开始，使用相同 30 道 evolution、相同 3 份题序、相同 7 个 checkpoint 机会和完整 20 道 val；每个变体独立选自己的最佳状态，不能借用 full method 的最优位置。其他开关、任务材料与总资源上限保持不变。global-only attribution 必须能通过审计过的接口获得相同合法证据，不能故意只给截断摘要。

JIT-matched 使用同一生成模型和执行模型的原生 JIT runtime；明确这是模型对齐的适配对照，不是原 JIT-27B 论文分数复现。rubric-fixed 必须向固定 Analyst/Evidence/Writer 组织提供同样来源的预测要求，使用固定 single-pass harness；现有不含 rubric 的 fixed-team pilot 不能改名字替代它。

G/GO 使用 full method 已选出的 3 个状态，各在 33 道 test 上重复 3 次。每个状态/题目/重复只生成一次 quality-only `R_star`，两组共享其文本哈希与证据包。G 的组队器和代码生成器不能看到它，必须等团队和 harness 冻结后才注入 actor 上下文；GO 在构建时可见。两组执行时得到完全相同的指导，冻结后不得改角色、依赖或代码。这个对照需要新的信息流边界，不能用简单的 rubrics 开关冒充。

Skill-MAS、Meta-Team 是建议增加的外部方法比较，每个采用同样的 30/7/20/3 次进化选择日程与 3 次 test 重复，但必须先固定作者实现或明确适配、审计预算和材料条件。未实现时不填表、不用固定团队冒充。外部 benchmark 和自由联网轨道需要另行冻结完整协议；若看过本轮 test 后才设计，只能标为探索性。

## 公共证据与模型资源

主轨道定义为 **ResearchRubrics 任务上的受控共享证据实验**。每题先由固定检索器仅根据公开题面构建一次证据包，所有方法、checkpoint 和重复使用同一份。禁止根据 private rubrics、答案或评分改查询、挑材料。这样将主要比较集中在质量预测、组织生成和经验复用，而非搜索引擎时变结果。它不是不受限制联网的官方 leaderboard 设置。

检索器使用同一执行模型，温度 0，一次最多 4,096 输出 tokens 的调用生成最多 4 个查询。每查询取前 5 条结果，按查询顺序和排名去重，最多抓取 8 个不同页面，并纳入公开附件。固定文本抽取和来源顺序，采用各来源轮流截断，证据包总上限 32,768 个 `tiktoken cl100k_base` tokens，并固定包版本与编码哈希。这个数字是统一的材料长度计量，不冒充代理模型的实际 tokenizer 或账单用量。保留 URL、日期、定位信息和失败通知，不在看过分数后补换材料。明确题目时间截止条件，保存检索时间、原始返回与内容哈希。每次执行只能读取本题证据包，不能读其他题材料或 evaluator 数据。

生成器、global/local analyzer、executor 固定为 `deepseek-v4-flash-vision`，主 judge 固定为 `claude-sonnet-4-5-20250929`，均温度 0。代理服务的名字不等于已核实版本，正式启动前必须保存服务身份、请求配置及可取得的版本信息；不可中途换端点或模型再当成同一个条件。题序种子不宣称能控制供应商采样。

本方法最多 3 个执行角色、并行度 2、每角色 1 次模型调用、1 轮执行前局部规划；Writer 单次读取完整 ledger。每次 JIT 生成 1 个候选，最多 2 次角色调用前的接口修复。输出上限为 meta/global/local 各 16,000、executor 8,192、judge 4,096 tokens。单任务上限 200 次模型尝试、200 万账本 tokens，请求超时 180 秒、执行超时 600 秒。主轨道 actor 不额外联网，证据准备成本单列。JIT 对照在相同总推理上限下保留其原生调用组织，不强改成 single-pass 再称原生方法。

共同上限不等于实际计算相等。论文分别报告证据准备、构建与执行、归因更新、checkpoint selection、最终 judge 的调用数、tokens、工具次数、时间及故障；未知价格保持空值。复用后的实际费用和名义执行额度都报告。共享证据的预处理不视为免费，同时提供部署时每题需要承担的证据准备成本。

## 工作量与执行顺序

| 阶段 | 名义任务执行单元 |
|---|---:|
| Full 进化 | 3 × 30 = 90 |
| Full val | 3 × 7 × 20 × 2 = 840 |
| Full selected、C30、C0 的 test | 297 + 297 + 99 = 693 |
| Direct、JIT-matched、rubric-fixed 的 test | 3 × 99 = 297 |
| 主实验合计 | 1,920 |
| 每项进化消融 | 90 + 840 + 297 = 1,227 |
| 三项进化消融合计 | 3,681 |
| G/GO | 3 × 33 × 3 × 2 = 594 |
| 必做实验总计 | 6,195 |

这些是预登记的任务尝试单元，不是 API 请求数，也不是保证成功的任务数。完全相同状态的结果复用可能减少实际执行数。共享证据准备、297 份共享 `R_star` 的生成、judge 重试和人工审计另行核算。Skill-MAS 和 Meta-Team 若纳入，每个另外增加 1,227 个名义单元。

执行顺序为：development 上补齐并冻结全部必做实现 → 冻结协议与材料 → 完成所有进化与 val 选择 → 封存选中状态 → 分批生成全部 test 与 G/GO 答案 → 一次性解封评价 → 统计与人工审计。中途发现代码缺陷或服务漂移可暂停，但不可静默改代码后混合结果；必须记录新的运行版本。已看过 test 后的继续调优需要新的独立确认数据。

人工审计选 `splits_v2.json` 中按公开任务 ID 哈希固定的 10 题，审阅 ours-selected 的 run0/repeat0、C0/repeat0、JIT-matched/repeat0，共 30 份答案。两名评审独立使用匿名化答案和固定官方 rubrics 评价，报告一致率与分歧，第三人仅裁决分歧；不按模型分数挑成功或失败例子，也不把意见反馈进经验。

## 实现就绪条件

当前代码已经具备直接经验写入、历史快照、只读存储、单次执行、逐条 rubric 评价与恢复去重。但**周期 checkpoint scheduler 和正式 VAL selector 尚未实现**。`run("evaluate")` 仅接受 test 集；正式 driver 必须保留原 split，显式核查 val 成员后只读执行，不能把 val 临时改名为 test。`MASConfig.seed` 也不是供应商随机采样控制。

正式运行还必须补齐：checkpoint/task/repeat 日志与失败推进、完整固定 val 的保守排名及同分规则、证据包与隔离环境、所有 baseline 和 G/GO、test 提交封存及评分延迟释放。新增 runner、selector 和 evidence 文件也必须单独纳入哈希；仅现有核心代码指纹不够。

公开题面去重、语义近重复及来源/时间审查仍是启动条件。相同主题本身不等于泄漏，本实验只声称任务级泛化，不声称 topic-disjoint。若发现真正近重复或来源答案泄漏，应在任何正式调用前发布版本化修订；不能看过分数再改变 18/30/20/33 或排除困难题。

## 与一手资料的关系

JIT 的静态与流式推理区分见[原论文第 4.2 节](https://arxiv.org/html/2608.25593#S4.SS2)。本协议采用独立验证选择后冻结测试，与流式任务间持续更新分开报告；本文的任务配额、checkpoint 周期与选择规则是本项目的预登记设计，不声称来自 JIT 官方划分。
